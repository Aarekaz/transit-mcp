# Changelog

All notable changes to Metro MCP will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added
- `skills/transit-mcp/SKILL.md`, an agent skill: which tool answers which question, names meaning several places, presenting results, and rechecking a planned trip before the rider leaves.
- `find_transit` searches every region when no coverage is given, and lists regions and their capabilities when called with no arguments (or only `coverage`). Names fold common spellings (Street/St, Avenue/Av, Square/Sq, 42nd/42, punctuation), match words in any order and ignoring filler (station, stop, metro), and tolerate small misspellings. When nothing matches, `suggestions` (and a not-found error's candidates) carry the closest names, never resolved on their own.
- DC stations answer to WMATA's published names ("Gallery Pl-Chinatown", "Chinatown", "Convention Center", "Adams Morgan"…), generated by `scripts/import-wmata-station-names.ts`.
- A timetable the post-publish canary rolled back comes back on its own once the live feed has moved onto it (`rollForwardSchedules`, every 5 minutes): providers publish the next timetable before the service day it starts.

### Changed
- A name that matches no stop exactly but matches a station and street stops named for a cross street ("Embarcadero": the BART station and "The Embarcadero & Folsom St") means the station; street stops beside it join its place and are never offered as a separate choice. Stops named for a station and more ("San Francisco Ferry Building Gate G") join it up to 800 m away. SF "Chinatown" now finds Chinatown-Rose Pak; "Coney Island", "Millbrae", "Van Ness" and "West Portal" resolve directly; a full corner name still finds that corner.
- Server instructions open by naming the regions served now and what each runs ("Live transit for the SF Bay Area (BART, Muni, Caltrain…), Washington DC (Metrorail, Metrobus) and New York (subway, LIRR, Metro-North, buses)"), so a model reaches for these tools rather than a web search; a dark region is never named.
- A name a rider gives with its operator ("16th St Mission BART", "Penn Station LIRR", "Palo Alto Caltrain Station", "Pentagon Metrorail") matches the rest of the name among that operator's stops when no stop name starts that way. Each region lists its operators' names (`operators`: 511 operator IDs in SF Bay, feeds in NYC and DC).
- A name a rider gives with where it is, its direction or its line ("14 St, Manhattan", "Metro Center DC", "Pentagon on the Blue Line", "Herald Square uptown", "14 St on the 1 line, uptown platform") matches the name without them when no stop name starts that way, preferring stops on the line named ("Canal St on the 6" is the 6's Canal St). Each region lists its `localities` (boroughs, cities, states). Words all found in one stop's name stay part of it ("Oakland Airport"), and a locality before the name ("San Francisco 4th and King") is dropped only when nothing matches with it.
- `get_service_status` takes a line by name with its coverage (`ref: "L"`, `"Red Line"`): a line named exactly so wins over IDs that also match, and one line copied into several feeds is one line.
- `plan_trip` takes `maxWalkMetres` above 800 as 800 instead of refusing the call.
- Server instructions open with the everyday path (pass the rider's words; which tool for which question) within the first 500 characters, then how to keep a rider posted. They no longer tell agents to call `find_transit` before every question.
- Results lead with the answer: `sources` and `attribution` come last, each source appears once, and timetable sources cite only the feeds the answer names (a subway trip no longer lists every bus feed). `plan_trip` itineraries open with times, status, transfers, walking and `steps`; the exact `legs` follow.
- A place name resolves to a place, not a stop. A name for one place (a station complex, stations within about 400 m, or every stop a reviewed alias names, such as SFO's terminals) plans from or to all its stations, and departure, vehicle and status boards cover all its stations in a network; `otherStations` lists the same place in other networks (the LIRR at Penn Station). A name for different places gets the best trip from each (up to three) in `plan_trip`, labelled in `reading` and explained in `notice`; the other tools return `ENTITY_AMBIGUOUS` with a question a rider can answer.
- `plan_trip` no longer asks the user to choose stop IDs through elicitation. `SELECTION_DECLINED` is gone.
- `coverage` is a closed list in every global tool's schema: `dc`, `nyc`, `sfbay`, or a region's own name ("SF", "Washington DC"), like the original tools' `city`. Models pick it from the list; anything else is refused with the valid ids.
- Coordinators keep live data warm 06:00-23:00 in each region's local time, and poll on demand overnight (a simulation against measured costs: ~4% cold answers, about half the plan's Durable Object time).
- Live data on a first question: outside service hours coordinators poll only while read (10 minutes), and a cold read for a stop answers from the agency's document as soon as it arrives, matching only trips on routes through that stop; the whole snapshot follows from the same request. Coordinator reads have a 30 s deadline, after which a tool answers from the timetable, labelled.
- Realtime snapshots are kept gzipped in each coordinator's own storage instead of R2 (which cost about 1.5 million writes a day).
- Rider-facing times (departures, arrivals, vehicles, alert periods, outages) are local to the agency with their offset; provenance stamps stay UTC.
- SF Bay's timetable-identity threshold is 50% (was an uncalibrated 95%, which refused live data on ordinary nights).
- Agency errors in the original tools say what the caller can do; `get_bus_predictions` validates the 7-digit stop ID.

### Fixed
- Rechecking a planned trip (`get_service_status` with `itinerary`) judges it on current times: a train running a few seconds or minutes off keeps the journey valid as long as every change is still made. A missed change is `MISSED_CONNECTION` on that transfer. Before, any change in a predicted time failed the whole journey with `ADJUSTED_TIME`.
- A recheck reads live data only for the feeds the trip rides, and checks each leg against its own feed's observation time. Before, a Metrorail trip failed with `REALTIME_PROVENANCE` whenever the Metrobus feed was a few seconds older.
- `get_service_status` accepts `coverage` beside a `ref` or `itinerary` when it names their own region, instead of refusing the call.
- Journeys no longer walk back and forth between a station's co-located platforms (NYC's A27N to A27S and back) or hop to one on the way out; the same rides reached by different walks are one journey, the shortest kept.
- A walk between two stations that share a name ("34 St-Penn Station" to "34 St-Penn Station") names each by its lines in `steps`.
- Every time in a `plan_trip` itinerary is in the agency's local time with its offset; walks and journey totals were in UTC.
- `find_transit` and `get_service_status` advertise one flat input object instead of a union. Clients flatten a top-level union, often to its last branch, so models were told `query`, `ref` and `stop` were never allowed. Combinations that don't fit (`ref` with `query`, `stop` without `coverage`…) now return `INVALID_ARGUMENTS`, saying what to send.
- Elevator and escalator outages were counted once per timetable in a coverage (twice in DC, about nine times in NYC).
- Live data fetched while a question waited was judged against the question's own clock and rejected; timestamps up to 120 s ahead now count as new.
- Network journey planner: `plan_trip` searches every line of DC, NYC and SF Bay, buses included, over compact timetables a cron builds in R2 (`compact/<coverage>/`), then plans and validates the proposed lines with the exact planner. Switch: `TRANSIT_NETWORK_PLANNING`; without its compact bands a coverage plans as before.

- SF Bay Area (511 SF Bay regional feed, every operator): departures, service alerts and vehicle locations through the global tools. Journeys there are planned by the network planner only; until its compact bands are built, `plan_trip` returns `PLANNING_UNAVAILABLE` with `routeHints`.
- Guided planning: `plan_trip` takes `routes`, up to four route refs to ride, and finds the actual trips, boarding stops, transfers and walks on only those lines, validated like any other itinerary. It works in every coverage, including SF Bay and buses. When a plan finds nothing (`PLANNING_UNAVAILABLE`, `SCOPE_LIMIT_EXCEEDED` or no journey) it returns `routeHints`: the lines near each end and the `direct` lines serving both.
- Itineraries carry rider `steps` (walk, ride, get off) alongside the legs.
- "Next train from A to B": `get_departures` accepts `toStop`/`toStopRef` and lists only trips that go on to that stop, each with its `arrival`.
- `find_transit` ranks candidates (exact names and reviewed place names such as SFO, Union Square, Penn Station, Grand Central and Dulles, then stations, then rail before bus) and describes each stop with `stopType`, `modes` and `routeNames`.
- Step-free journeys in DC and NYC. `plan_trip` with `accessibility: "step_free"` boards, alights and changes only at platforms reachable without stairs and avoids stations cut off by a current elevator outage; the validator rechecks every leg. It refuses with `ACCESSIBILITY_UNAVAILABLE` without a current elevator report and `ENDPOINT_NOT_STEP_FREE` when an endpoint has no step-free platform. NYC station access comes from MTA's station list, including stations accessible in one direction only.
- Elevator and escalator outages in `get_service_status` for a station (its whole complex), line, trip, itinerary or city: on the step-free path or not, whether a backup elevator exists, whether it blocks step-free travel, since and estimated return, and MTA's alternative route. Ingested from WMATA ElevatorIncidents and MTA's elevator/escalator feeds every five minutes. `get_departures` rows and station details report `stepFree`. Both coverages now report the `accessibility` capability.
- Long Island Rail Road and Metro-North join the `nyc` coverage, Metrobus and NYC buses (every borough and MTA Bus Company) join `dc` and `nyc`. Journeys plan across subway, LIRR, Metro-North and Metrorail, changing on foot at stations such as Penn Station and Grand Central; LIRR and Metro-North departures show the track. Buses serve departures, vehicle locations and alerts; the open search does not plan them (a city's bus network does not fit one isolate's search), so bus journeys are planned along named lines with `routes`. NYC bus realtime uses MTA Bus Time and stays off until `MTA_BUS_API_KEY` is set.
- A coverage can hold several feeds: each feed is validated, built and refreshed at the edge on its own and composed into the coverage's one manifest, and each realtime source has its own coordinator and budget. Metro-North trips match by train number and civil departure; one Bus Time document is matched across six timetables. Dense feeds refresh at the edge by first splitting stop_times by band, so no step holds a bus day at once.

- NYC train IDs. `get_vehicle_status` returns each train's `trainId` (MTA's, such as `1A 1023 207/FAR`: line, scheduled origin time, origin/destination; WMATA's number in DC), read from NYCT's protobuf extension in the documents already polled. `find_transit` resolves `train <id>` to the trip that train is running, ignoring case and spacing.
- DC Metro and the NYC Subway now serve the five global tools in production: trip planning, departures, service status, and train locations. Planning uses the published WMATA and MTA timetables with live predictions; every itinerary is independently validated.
- NYC departures read all eight subway feeds together and include rerouted trains and trains missing from the timetable, marked as observed. If any feed is missing or frozen, NYC falls back to the timetable rather than showing a partial picture.
- Timetables refresh at the edge: the existing cron checks WMATA and MTA cheaply and a Cloudflare Workflow rebuilds only when a new timetable is published. Updates that remove most of a day's service are rejected; updates that make live matching worse roll back.
- `get_departures` accepts a station name with `coverage`. Station complexes (for example Times Sq-42 St or Grand Central-42 St) resolve as one place; departure rows include `routeName` and `stopName`.

- Versioned 511 SF Bay regional GTFS artifacts and a quota-aware realtime feed hub back the SF Bay coverage. Results retain freshness metadata and attribution to 511 SF Bay and participating operators.
- Five always-registered global tools, deterministic planning, independent itinerary validation, and synthetic SF/DC/NYC corpora. The frozen local MCP conformance runner reports required failures separately from optional extensions. See `docs/global-transit-verification.md` for the unpassed launch gates.

### Changed

- Production enables DC and NYC global coverage (`TRANSIT_COVERAGE_MODES`) and SF Bay (`SFBAY_MODE=on`, planned by the network planner only); preview leaves DC and NYC off and SF Bay dark. The server registers 18 tools (13 compatible plus five global) and four transit resource templates; the legacy tools are unchanged.
- Faster global tools: planner transfer rules are indexed (NYC plans about 10x faster), entity lookups are built once per timetable, and city-wide alert results report exact counts with bounded detail.

- The landing page, docs, README and `/info` describe all three regions: New York, DC and the SF Bay Area, with the honest limits.
- Rebranded to Transit MCP with `https://transitmcp.com` as the canonical origin. Pages, `/info` links, and the reported MCP server name (`transit-mcp`) now use the new brand.
- MCP trust checks accept requests on the canonical origin or on any HTTPS, default-port hostname in `MCP_ALLOWED_HOSTNAMES`. Production allowlists `transitmcp.com` and `metro-mcp.anuragd.me`, so `https://metro-mcp.anuragd.me/mcp` keeps working.
- Clearer model-facing descriptions for `get_station_predictions`, `get_all_stations`, and `get_incidents`. Tool names, input schemas, and output schemas are unchanged.

### Added

- Workers Analytics Engine usage counts (`ANALYTICS` binding, `mcp_usage` dataset): one data point per legacy `initialize` and `tools/call` built only from finite allowlisted categories. Session and correlation identifiers are excluded; the index is empty. Counts describe recorded requests, not unique users or proven successful answers.
- Server identity metadata (`title`, `description`, `websiteUrl`, `icons`) and model-facing `instructions` in `initialize` and `server/discover`.
- `server.json` for the official MCP Registry (`com.transitmcp/transit-mcp`, streamable HTTP at `https://transitmcp.com/mcp`).

### Security

- Upgraded `@modelcontextprotocol/server` and `@modelcontextprotocol/client` to 2.3.1 and `agents` to 0.28.1, picking up fixes for GHSA-46jr-4wx8-v453 (memory exhaustion during validation), GHSA-f897-62hf-6gxq, and GHSA-jm63-cq47-j5jp. `@modelcontextprotocol/sdk` stays at 1.30.0 so the Transit Board app bundle is byte-identical.

- `get_vehicle_status` locates NYC trains. NYCT reports each train's station and status inside the trip feeds already polled, so this adds no MTA requests. Trains are listed by line, by dated trip, or by station; each carries the station it is at or heading to, the station it last served, and its destination. A train MTA still reports as stopped after its own prediction has moved on is shown heading to the predicted station.

### Fixed

- NYC live predictions now reach the 7, L and Staten Island Railway, and most F and G trains. Those lines publish a short trip ID (`059150_7..S`) for the scheduled `..._059150_7..S97R`; it is matched only when it names exactly one active scheduled trip. Live matching rose from 69% to 82% of NYC trains.
- Route names are the ones riders use: WMATA's single-letter short names become the line name ("Red", not "R").
- A station complex now covers every station in it: departures at Times Sq-42 St include the 1/2/3, 7, N/Q/R/W and shuttle, not just the first station found.
- Long NYC trips (Inwood-207 St to Coney Island) and plans whose window crosses into a third timetable band no longer exceed the planner budget. The router interns leg sequences instead of keeping a signature string per label, and the decoded-shard charge is measured (2.2x file size) rather than assumed (8x). Across 240 NYC plans at every half hour of a day, none is refused with the default window.
- NYC trip planning no longer refuses rush-hour trips. The planner charged its memory budget as if it copied every live prediction; it only indexes them.
- `get_elevator_incidents` no longer fails when WMATA omits a station name for an outage; the station code is used instead.
- DC service alerts no longer go stale while WMATA has an active alert. WMATA sends alert severity in a field the GTFS-Realtime spec reserves for text; the decoder now drops alert fields with the wrong wire type, records a warning, and keeps the alert. Any other malformed feed is still rejected.

## [6.0.0] - 2026-08-21

### Breaking

- Metro MCP is now anonymous. `/mcp` and `/sse` accept public MCP traffic with no login, client credential, bearer token, or OAuth flow; stale `Authorization` headers are ignored.
- `/info` advertises MCP `2026-07-28`, anonymous authentication (`{ type: 'none' }`), the `/mcp` and `/sse` endpoints, canonical `Aarekaz/metro-mcp` repository links, and privacy, terms, and support pages at `metro-mcp.anuragd.me`.
- Retired account and credential endpoints are no longer advertised. The conformance runner now invokes frozen `@modelcontextprotocol/conformance@0.2.0-alpha.11` directly with only `MCP_CONFORMANCE_TARGET_URL`.

### Added

- Cloudflare request limiting of roughly 300 requests per 60-second window per source-IP key per Cloudflare location. Shared egress IPs group clients, and enforcement is eventually consistent; it is not a dedicated user quota.
- Canonical privacy, terms, and support links for the public service.

### Preserved

- The stateless MCP runtime, 13 tools, 3 resources, 3 prompts, Apps enhancement, request cancellation, MRTR state, cache hints, and rollback assets remain intact.

## [5.0.0] - 2026-08-13

Metro MCP 5.0 upgrades the remote server to MCP `2026-07-28` and a request-scoped SDK v2 architecture. The transit surface remains exactly thirteen read-only tools, three resources, and three prompts.

### Added

- MCP `2026-07-28` request metadata, discovery, cache hints, cancellation, and Multi Round-Trip Requests (MRTR) for ambiguous station selection.
- Cloudflare's OAuth Provider with Client ID Metadata Documents first, temporary DCR fallback, explicit `transit:read` consent, PKCE, RFC 9207 issuer identifiers, RFC 8707 resource binding, RFC 9728 discovery, rotating refresh tokens, and revocation.
- Workerd protocol/OAuth lifecycle coverage plus a loopback-only authenticated conformance runner pinned to `@modelcontextprotocol/conformance@0.2.0-alpha.11` and its frozen `2026-07-28` requirements.
- Dedicated production and preview `OAUTH_KV` bindings and separately configured GitHub OAuth apps/callbacks.

### Changed

- `/mcp` is the only canonical MCP resource. Modern MCP 2026 operations are stateless and do not require `initialize`; ordinary MCP 2025 stateless tools, resources, and prompts remain supported.
- `POST` and `OPTIONS /sse` are rewritten to `/mcp` before authorization. `/sse` is not an OAuth audience.
- Access tokens last at most 60 minutes. Refresh tokens last at most 30 days and rotate on use. Bearer credentials are accepted only through the Authorization header.
- DCR remains available temporarily and sunsets on **2027-06-30**; CIMD or pre-registration is preferred.
- Protocol work no longer creates or addresses a Durable Object. The original `MetroMcpAgent` export, namespace, and `v1` migration remain inactive for rollback.

### Breaking

- Legacy GET SSE, DELETE, slash variants, and session message URLs now return `405`; there is no persistent SSE stream, resumability, or server push.
- Tokens without an audience, tokens bound to `/sse`, and clients from the old DCR store must reauthorize against canonical `/mcp`.
- Compatible legacy JWTs already bound to `/mcp` expire at the earlier of their embedded expiry and **2026-11-30T00:00:00Z**.
- The old active `MCP_SESSION`, `OAUTH_CLIENTS`, and `RATE_LIMIT_KV` bindings are removed. Self-hosters must configure a dedicated `OAUTH_KV`, `global_fetch_strictly_public`, and the new origin/allowlist/MRTR environment contract.

### Deferred

- MCP Apps and embedded interactive UI are explicitly deferred to the next PR.

## [4.0.0] - Durable Objects rearchitect via cloudflare/agents McpAgent

A foundational rewrite of how Metro MCP serves sessions. The MCP API
surface stays additive (clients keep working unchanged), but the
infrastructure underneath the `/mcp` and `/sse` endpoints is replaced.

### Why a major bump

The KV-backed, request-per-message session model from 3.x is replaced
by a Durable Object that holds the session for its lifetime. This
unlocks capabilities the MCP 2025-06-18 spec assumes a server can do
but the old infra couldn't: server-initiated push, resumability,
elicitations, subscribable resources.

### Added

#### Durable Object-backed sessions (cloudflare/agents `McpAgent`)
- New `MetroMcpAgent` class extends `agents/mcp`'s `McpAgent`, which
  itself extends `Agent → DurableObject`. One DO instance per
  `Mcp-Session-Id`.
- Hibernatable WebSocket transport — DO evicts while idle, no
  billing during quiet periods. Wakes on incoming messages.
- `DurableObjectEventStore` — built into McpAgent — handles
  `Last-Event-ID` replay for resumable streams.
- `MCP_SESSION` DO binding in `wrangler.jsonc` with first-time
  migration `tag: "v1", new_sqlite_classes: ["MetroMcpAgent"]`.

#### New MCP capabilities (resources, prompts, elicitations, progress)
- **Resources** — three `transit://` URI templates:
  - `transit://stations/{city}/{id}` — station metadata
  - `transit://routes/{city}/{id}` — route info
  - `transit://incidents/{city}` — live service advisories
  - `resources/list` for the incidents template; stations/routes
    omit list because the catalog is large (use tools to discover).
  - `resources/subscribe` is declared at the SDK level but the
    incident poller that fans out `notifications/resources/updated`
    arrives with Phase 2.5.

- **Prompts** — three canned templates:
  - `service-briefing(city, lineCode?)` — 3-sentence status briefing
  - `commute-planner(city, from, to)` — multi-step real-time plan
  - `accessibility-check(stationNames)` — DC elevator outage scan

- **Elicitations** — `elicitation/create` is now used in
  `get_station_predictions`. When a station name resolves to multiple
  matches (e.g., "Times Square" → 127, R16, 725), the server asks the
  user which one instead of silently picking the first. Clients that
  don't declare elicitation capability fall back to the legacy
  first-match behavior automatically.

- **Progress notifications** — `notifications/progress` for
  `get_all_stations` when the client opts in via
  `params._meta.progressToken`. Two checkpoints: "Fetching…" and
  "Normalizing…". The NYC catalog is ~600 stations so the visibility
  matters for long-running clients.

#### Honesty in transport advertisement
- `supportsServerPush: true` (was `false` — hibernatable WS push works)
- `supportsResumability: true` (was `false` — DurableObjectEventStore)
- `note` tightened to reflect actual DO-backed transport

### Changed

#### Infrastructure
- `wrangler.toml` → `wrangler.jsonc`. IDE schema validation,
  inline comments, no nested-table indent sensitivity.
- `compatibility_date: "2025-12-25"` → `"2026-04-07"` for the
  hibernatable WebSocket auto-Close-reply runtime behavior.
- `MCP_SESSIONS` KV namespace deprecated. Sessions live in the DO.
  KV binding kept as optional during the drain window
  (existing 24h-TTL entries are harmless); remove in 4.1.

#### Tool implementation
- All 13 tools migrated from the hand-rolled `MCP_TOOLS` array +
  `MCPHandler.handleToolCall` switch to `server.registerTool(...)`
  calls inside `MetroMcpAgent.init()`.
- Schemas now expressed in Zod (the SDK's idiomatic path), which
  derives JSON Schema automatically.
- Tool result shape preserved exactly from 3.2.0:
  `{ content: [...], structuredContent: {...} }`.

#### Build / DX
- Node `--max-old-space-size=12288` baked into `build`, `lint`,
  `type-check` scripts. Zod's deep generic inference for the SDK's
  `registerTool` signature OOMs at the default 4GB heap once you
  have 14+ typed tool handlers. GitHub Actions default runners
  default to 7GB — bump there if you use CI. Long-term fix is
  project references or switching to AnySchema.
- `package.json` 3.2.0 → 4.0.0.

### Removed

- `src/mcp-handler.ts` — replaced by `MetroMcpAgent.init()` handlers
- `src/mcp-tools.ts` — tools registered inline now
- `src/mcp-types.ts` — no longer used (SDK provides equivalents)
- `src/utils/sse-formatter.ts` — SDK handles SSE framing
- `src/utils/` — empty after the above
- `tests/unit/mcp-tools.test.ts` — 16 tests against the deleted array;
  type-check now enforces tool shape via the SDK's registerTool generics
- The POST `/` MCP alias. Clients use `/mcp` (recommended) or `/sse`.

### Deferred to Phase 2.5

- **DO-runtime tests** via `@cloudflare/vitest-pool-workers`. The
  dependency is installed and ready; integration tests against a
  miniflare workers runtime land in a follow-up PR so they can be
  exercised against a real staging deploy. The existing 103 unit
  tests (auth, RFC 8707 audience binding, middleware, config) cover
  the highest-risk non-MCP code paths.
- **Incident poller** that publishes `notifications/resources/updated`
  to subscribers of `transit://incidents/{city}`. Needs a Cron-triggered
  DO that polls upstream feeds and fans out — non-trivial design.
  Until then, incident resources are read-on-request.

### Backwards compatibility

- MCP API surface: every tool keeps its name, inputs, outputs, and the
  `content + structuredContent` result shape. Phase 1's tool annotations
  and outputSchema declarations are preserved (now via the SDK's typed
  API rather than the static array).
- OAuth flow: unchanged. RFC 8707 audience binding from 3.2.0 continues
  to work; the verified user identity flows into the DO via `ctx.props`.
- JWT tokens issued under 3.x stay valid for their remaining 90-day TTL.
- Existing client integrations (Claude Desktop, mcp-cli, etc.) need no
  changes.

### Migration steps for self-hosters

1. `bun install` (or `npm install`) to pick up the new deps.
2. `cp wrangler.jsonc.example wrangler.jsonc` if running fresh; the
   existing config is straightforward to translate.
3. Set `compatibility_date: "2026-04-07"`.
4. Add the `durable_objects` and `migrations` blocks (see
   `wrangler.jsonc.example`).
5. `bunx wrangler deploy` — the migration runs automatically and
   creates the `MetroMcpAgent` namespace.
6. The `MCP_SESSIONS` KV namespace is no longer referenced and can be
   deleted in a follow-up once any in-flight sessions have drained.

## [3.2.0] - MCP 2025-06-18 alignment + RFC 8707 audience binding

### Added

#### MCP 2025-06-18 surface
- Tool `title` (human-readable display name, separate from machine `name`)
- Tool `annotations`: `readOnlyHint`, `idempotentHint`, `openWorldHint` declared on
  every tool. All Metro MCP tools are read-only live-data queries.
- Tool `outputSchema` declared for every tool. Clients can validate responses
  and integrate typed data without re-parsing.
- Tool results now emit `structuredContent` alongside `content`. The text
  payload is the JSON serialization of `structuredContent`, per spec SHOULD.
- Normalized prediction shape: `minutesAway: integer | null` +
  `arrivalStatus: 'ARRIVING' | 'BOARDING' | 'DELAYED' | 'SCHEDULED'` instead
  of the mixed `"3 min" | "ARR"` string. Clients can now sort/compare and
  render however they want.

#### RFC 8707 — Resource Indicators (audience binding)
- `/authorize` accepts an optional `resource` parameter (must be an absolute URI)
- Tokens issued from such flows carry a JWT `aud` claim bound to the canonical
  MCP resource URI (`{scheme}://{host}/mcp`).
- Each authenticated request verifies that the token's audience matches the
  request's canonical resource. Mismatch → 401.
- `/.well-known/oauth-authorization-server` now advertises
  `resource_indicators_supported: true`.

#### Honesty in the transport advertisement
- Server-info now distinguishes:
  - `supportsSSEResponses: true` — POST → SSE response format works
  - `supportsServerPush: false` — persistent GET-stream push is not implemented
  - `supportsResumability: false` — Last-Event-ID replay is not implemented

### Changed

- Single source of truth for `SERVER_VERSION` and `MCP_PROTOCOL_VERSION` in
  `src/config.ts`. Removed hardcoded `'3.1.3'` and `'2025-06-18'` strings from
  `router.ts` and `mcp-handler.ts`.
- `package.json` version bumped 3.1.1 → 3.2.0.

### Deprecation timeline

- **Legacy tokens (no `aud` claim) are grandfathered.** They continue to work
  with a `console.warn` deprecation log until their natural 90-day TTL expires.
  Re-authenticate with a `resource` parameter to bind future tokens.
- Clients SHOULD send `resource={mcp_endpoint}` on `/authorize`. Future major
  versions may require it.

### Backwards compatibility

- All new tool fields (`title`, `annotations`, `outputSchema`, `structuredContent`)
  are additive. Clients that only know MCP 2025-03-26 keep reading `content[0].text`
  unchanged.
- The text payload is now the serialization of `structuredContent` (per spec).
  It is no longer pretty-printed with 2-space indentation — clients that parse
  it as JSON are unaffected; clients that displayed it raw will see compact JSON.
