Docs for the live transit MCP.

Transit MCP lets an AI answer transit questions in New York, Washington DC and the SF Bay Area from the agencies' own timetables and live train data. You point your client at one URL. There's no key and no account. This page covers setup, the tools, how the thing works underneath, and where the data comes from.

Metro MCP is now Transit MCP. Same server, new home at transitmcp.com. The old endpoint, https://metro-mcp.anuragd.me/mcp, still works and will continue to be supported.

Connect an MCP client

The endpoint is anonymous Streamable HTTP. No login is required, and no token or OAuth flow is required either. If your client sends an old Authorization header, it's ignored.

Claude Desktop / Cursor config 
{
  "mcpServers": {
    "transit-mcp": {
      "url": "https://transitmcp.com/mcp"
    }
  }
}

Claude Code

claude mcp add --transport http transit-mcp https://transitmcp.com/mcp

Codex CLI

codex mcp add transit-mcp https://transitmcp.com/mcp

Anything else

Name transit-mcp, URL https://transitmcp.com/mcp, transport streamable-http. It's also in the ChatGPT and Claude directories and the official MCP Registry as com.transitmcp/transit-mcp.

How it works

The short version: the server reads timetables it built ahead of time and corrects them with live data. The model you're talking to never guesses a time. It gets one from the server, with a label saying where it came from.

Two clocks

Every agency publishes two things. A timetable (GTFS) says what's supposed to run. A live feed (GTFS-realtime) says what's actually running. One changes a few times a day, the other every few seconds, so the server handles them separately.

The timetable is built ahead. When an agency publishes a new one, a background job turns it into small pieces: one set per service day, nine days of them, cut into three-hour bands. Nine because it's yesterday (for trains still running after midnight), today and the week ahead. A question about the 1 train at 9 a.m. reads one or two of those pieces, about a megabyte, instead of a whole city's schedule.

The live feed never stops. One coordinator per feed polls it (every 30 seconds for the subway) and keeps the latest snapshot in memory. When a question comes in, the live predictions are matched onto timetable trips, one trip at a time.

Live data only exists for trains that are running. Ask about Thursday and you get the timetable, and the answer tells you so. That's the whole of Fig 1.

Answers say what they are

Every result carries a status: realtime, scheduled_only or unavailable, plus asOf, the time the data was read. If a stop's live feed is down, you get the timetable marked scheduled_only, not a timetable passed off as live. Agents are told to pass the label on, so a rider hears "scheduled" when that's all there is.

The server owns facts, the model owns meaning

An agent passes the rider's own words: "Penn Station", "14 St on the 1", "Powell St, SF". Turning those into stations is the server's job. Matching is tuned for how people type: "Street" and "St" are the same, small typos still land, and a city or a line after the name narrows it down.

When one name really is two places (New York has several 86 St stations), the server doesn't pick. It sends back a question a person can answer, in place names, not IDs. The model does the part it's good at: working out from the conversation which one you meant, then saying the answer in plain words.

Fresh timetables on a $5 plan

This runs on Cloudflare's $5 Workers plan, and building timetables is the expensive part: a rebuild of the NYC subway takes a couple of minutes of CPU. MTA republishes that timetable roughly every hour, mostly to add planned work for the coming week. Rebuilding every time would use up the plan on its own. So:

  • If an upload's tables haven't changed, it's skipped. The server compares each table's checksum from the zip's directory, without unzipping anything. MTA does sometimes upload the same tables again.
  • A change that touches yesterday, today or tomorrow is built on the next check, within five minutes. Live trains are matched to today's trips by ID, so those can't wait.
  • A change that only touches later days waits up to six hours and goes in with the next batch.

To tell which days a change touches, the server diffs the 6 MB trips file against the published one. That takes about a tenth of a second, once per upload. If it can't tell (a change to stops or calendars, say), it rebuilds straight away.

Checking its own work

  • Every itinerary goes through a separate validator before it's returned: real trips, real stops, transfers you can actually make.
  • A new timetable is checked before it goes live. If live trains match it worse than the one it replaced, it's rolled back.
  • Every other day the server calls its own tools the way an agent would. If anything fails, it checks again every hour until it passes. The latest result is at /health/deep.
  • From outside Cloudflare, a GitHub Action calls the endpoint every five minutes and opens an issue if it stays down.

What runs where

PieceJob
WorkerThe front door. Serves the site and the MCP endpoint and runs the tools. Each MCP request runs in a request-scoped stateless runtime, so it does not support resumability or server push. The inactive MetroMcpAgent rollback class and v1 migration remain for rollback.
Durable ObjectsOne coordinator per live feed. Polls the agency and keeps the latest snapshot in memory, so a question never waits on the agency.
R2The timetable pieces. Each is named by its own checksum and checked on every read.
WorkflowsTimetable builds, one step per service day, so a big feed never has to fit in one request.
Rate limitingThe Cloudflare Rate Limit binding allows roughly 300 requests per 60-second window per source-IP key per Cloudflare location. Clients behind shared egress IPs share one count, and enforcement is eventually consistent.
Analytics EngineUsage counts. See below.

What gets recorded

One record per tool call: the tool, a rough category for the client software, how long it took, whether it worked, and which regions and feeds the answer drew on (nyc, mta_subway). Never what you asked, never your IP. The privacy page has the full list.

Tools

There are 18 Model Context Protocol tools. Every one is read-only and returns structured content, plus the same thing as JSON text for older clients. Start with these five. They work in all three regions.

ToolAsk itGood to know
plan_tripPenn Station to JFKReal itineraries from the timetable, with live times where there are some, and every leg validated. Add accessibility: "step_free" to avoid stairs and stations with a broken elevator right now. If it can't find a trip, it returns routeHints: the agent picks lines and asks again with routes.
get_departuresNext uptown 1 at 14 StA name covers the whole place, like all four stations at Times Sq-42 St. toStop keeps only trains that reach a destination. In New York, rerouted trains and trains missing from the timetable show up, marked as observed.
find_transitWhich Union Station?Finds stations, lines and train numbers. Leave out coverage and it searches every region. With no arguments it lists the regions and what each supports. Closest names come back as suggestions and are never treated as a match.
get_service_statusIs the Red Line OK?Alerts, elevator and escalator outages, and a recheck of a planned trip before you leave: pass the itinerary back exactly as plan_trip returned it.
get_vehicle_statusWhere's my train?Trains on a line, on a trip or at a station. DC trains report GPS. MTA reports stations, so an NYC train between stations has no position rather than a made-up one.

Names work the way people say them. "King Street" finds King St-Old Town, "42nd Street Times Square" finds Times Sq-42 St, and DC stations answer to WMATA's own names ("Chinatown", "Convention Center"). Times are in the agency's local time with its offset, such as 18:32-04:00.

New York covers the subway, the Long Island Rail Road, Metro-North and buses. Washington covers Metrorail and Metrobus. The Bay Area covers every operator in 511 SF Bay's regional feed: BART, Muni, Caltrain, AC Transit, VTA, SamTrans, the ferries and more, with attribution to 511 SF Bay and its operators. Trips change between modes on foot at places like Penn Station, Grand Central and Atlantic Terminal, and LIRR and Metro-North departures show the track.

The 13 older DC/NYC tools

They're still there, and still read WMATA's and MTA's APIs directly: search_stations, get_all_stations, get_stations_by_line, get_station_predictions, get_incidents, get_elevator_incidents, get_bus_predictions, get_bus_routes, get_bus_stops, get_bus_positions, get_train_positions (DC), and get_route_info, get_station_transfers (NYC). New agents should use the five above. The Transit Board app view covers these older tools only.

Hints for clients

Ambiguous station names can trigger MCP elicitation where the client supports it. get_all_stations sends progress notifications if you pass a progress token. Every tool is annotated read-only, idempotent and open-world.

Data sources

Everything comes from the agencies' official feeds. The five main tools use each agency's GTFS timetable, built as described above, plus GTFS-realtime feeds polled every 30 seconds to a few minutes. The 511 SF Bay feed shares one hourly request budget across every operator, so the Bay Area refreshes more slowly than New York or DC. The first question after a quiet spell can take a few seconds longer while a timetable loads, longest in the Bay Area.

HTTP endpoints

One Worker serves the site and the MCP API. All of it is public.

POST/mcp

The MCP endpoint, anonymous Streamable HTTP.

POST/OPTIONS/sse

Stateless alias for /mcp. GET /sse returns 405; it isn't a persistent stream.

GET/info

A JSON summary: regions, station counts, capabilities and the MCP endpoint.

GET/health/deep

The latest self-check: each tool call it made, how long it took, and what failed. 200 when it passed recently, 503 otherwise.

GET/llms.txt

A plain-text summary for agents.

GET/, /docs/

The landing page and this page.

Pairs well with

When the commute planner shows delays, your agent can handle the fallout too. call4me is an MCP server that makes real phone calls for you. It can call ahead to tell a restaurant you're running late, reschedule a doctor's appointment, or wait on hold for you. Add it next to Transit MCP in the same client and try something like "trains are delayed, call the restaurant and push my reservation 30 minutes."
